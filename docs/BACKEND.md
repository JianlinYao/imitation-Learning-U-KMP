# Local experiment management backend

The v0.6 service adds a real HTTP API and persistent SQL database around the
existing scientific CLI. It is a local, single-user experiment manager. It has
no account/permission system or public multi-tenant deployment configuration.
Scientific methods and the archived v0.5 benchmark records retain their original
meaning; adding the service does not turn simulation results into hardware data.

## Start

On Windows, extract the current repository into a folder and double-click
`run_server.bat`. It uses a project-local `.venv`, installs the server and
simulation extras, and starts the service with automatic browser opening.
Keep its console open; Ctrl+C stops the service. Subsequent runs reuse the
environment and the database in the same project directory.

```bash
python -m pip install -e ".[server,simulation]"
python -m imitation_learning server --workspace outputs/server --port 8000 --open-browser
```

Open `http://127.0.0.1:8000/`; interactive OpenAPI documentation is at `/docs`.
The service binds to loopback. Use a different port for another application and
a different workspace for another independently running experiment manager.
The original `serve` command remains a static report viewer; `server` starts
the new API and task executor.

## What is persisted

`outputs/server/experiments.sqlite3` uses SQLite WAL mode, foreign keys, bound
SQL parameters and one connection per operation. Schema version 1 contains:

| Table | Stored content |
|---|---|
| `jobs` | Validated request, effective algorithm configuration, lifecycle timestamps, state, exit status, summary and retry parent |
| `events` | Ordered state transitions and reasons |
| `metrics` | Queryable learning/simulation records, method/task/controller identifiers and numerical metrics |
| `artifacts` | Registered result paths and sizes |

Large trajectories, figures and HTML reports stay in each task's unique
`jobs/<id>/output/` directory; their catalog is stored in SQLite. Logs are UTF-8
in `jobs/<id>/task.log`. Configuration snapshots are generated by the server,
not supplied as arbitrary filesystem paths or shell commands.

## Lifecycle and execution

A new job is committed as `queued` before the HTTP 202 response. A supervisor
claims one job in a `BEGIN IMMEDIATE` transaction and launches the existing
`run` or `demo` command with `shell=False` in a separate Python process. Heavy
learning/physics computation therefore does not run in the request handler.
The first release executes one experiment at a time, with additional tasks
waiting in the durable SQLite queue.

States are `queued`, `running`, `cancelling`, `succeeded`, `failed`, `cancelled`
and `interrupted`. Cancelling a queued job prevents execution. Cancelling a
running job terminates its child process before publishing `cancelled`.
Completed metrics, artifact registration and the final state commit atomically.
An experiment that exits nonzero is `failed`; task-success metrics in individual
scientific records remain separately available.

Graceful server shutdown stops the active child and records `interrupted`.
On restart, queued tasks remain queued and unfinished active records are
marked interrupted. Abrupt OS/process termination is not a checkpoint/resume
guarantee: an orphan computation may require manual closure. Retrying creates a
new task ID and output directory, preserving the previous logs/results; it does
not continue a partially executed task. Existing CLI `--resume` remains a
separate feature. An OS-held workspace lock prevents two executor instances
from owning the same workspace concurrently.

## API

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/health` | Service/worker state and task counts |
| GET | `/api/catalog` | Supported methods, letters, tasks and defaults |
| POST | `/api/jobs` | Validate and enqueue a learning or learning+simulation job |
| GET | `/api/jobs` | List/paginate/filter by state |
| GET | `/api/jobs/{id}` | Request, effective config, state and summary |
| POST | `/api/jobs/{id}/cancel` | Cancel a queued/active task |
| POST | `/api/jobs/{id}/retry` | Create a new run from a finished task's settings |
| GET | `/api/jobs/{id}/events` | Lifecycle history |
| GET | `/api/jobs/{id}/logs` | Bounded tail of the process log |
| GET | `/api/jobs/{id}/metrics` | Paginated metrics, filtered by source/method |
| GET | `/api/jobs/{id}/artifacts` | Registered output files |
| GET | `/api/jobs/{id}/files/{path}` | Open a registered report or download a file |

Example request body:

```json
{"kind":"demo","letters":["A"],"methods":["KMP","U-KMP"],"points":80,"fold_limit":1}
```

`kind=learning` evaluates the selected tasks. `kind=demo` additionally tracks
one reproduction reference per letter/method with actual MuJoCo physics;
ordinary methods use fixed LQR and U-KMP uses covariance-aware LQR, with shared
duration within each letter. The demo requires the reproduction task and the
simulation extra. `fold_limit=1` is explicitly a partial evaluation; use 5 for
all folds. Defaults reserve 20% of outer-training demonstrations for empirical
interval calibration. Requests cannot choose arbitrary data/output/config paths.

Report links retain relative CSV/figure paths. Downloads are restricted to
registered files inside that job's directory; traversal, outside symlink targets
and unregistered files are rejected. Cross-origin mutations and unexpected
HTTP host names are rejected. Authentication and internet hosting are outside
this local service's current scope.

## Verification

```bash
python -m pip install -e ".[server,simulation]" httpx
python -m unittest discover -s tests -p "test_backend*.py" -v
```

Tests exercise concurrent queue claims, database reopen/recovery, exclusive
workspace ownership, validation, cancellation, process failures, graceful
shutdown/restart, metrics isolation and registered downloads. Real scientific
integration runs a learning job and a MuJoCo KMP/U-KMP demo through the HTTP API.
Lifecycle/UI fixtures are explicitly synthetic process outputs and are not
research results. The Chrome CI checks submission, reports, retry, validation
and mobile layout. Linux/Windows CI checks the backend; Windows also installs
and resolves arguments through `run_server.bat --help`.
